## Causa del bloqueo anterior

La conexión guardiana abría una transacción, obtenía cerrojos y ejecutaba la captura completa de las tablas dentro de esa misma transacción. La lectura de `pos.customers` conservaba ACCESS SHARE hasta el ROLLBACK final. Otra conexión intentaba ALTER TABLE, que necesita ACCESS EXCLUSIVE: ambas operaciones eran incompatibles. El guardián bloqueaba al propio migrador.

Ese problema no se resuelve ignorando la conexión propia en `pg_locks`, aumentando indefinidamente el timeout o añadiendo un advisory lock. [PostgreSQL documenta los modos incompatibles y su duración transaccional](https://www.postgresql.org/docs/17/explicit-locking.html).

El arnés anterior `.cache/automation/guarded-batch.mjs` quedó inhabilitado para producción. También se bloquearon las acciones de escritura del antiguo ejecutor privado `Invoke-CaiProductionSql.prepared.ps1` hasta que exista un ejecutor de producción revisado que implemente el nuevo procedimiento autorizado.

## Barrera de escrituras: permisos efectivos, sin cooperación del cliente

El inventario comprobó que los escritores de personal y de recordatorios ejecutan su DML bajo `pos_owner`. Sus funciones SECURITY DEFINER mantienen propietario/código conocidos; el único puente con otro propietario es el de identidad de 005, que no escribe datos. Las aplicaciones no tienen DML directo, `pos_owner` no tiene LOGIN ni privilegios elevados/membresías heredadas y no se permiten concesiones de columna o identidades de escritura adicionales no previstas. Las definiciones anteriores se comparan con la captura revisada; una función no revisada detiene el ensayo.

La barrera utiliza una retirada temporal de permisos ordinarios del propietario, que PostgreSQL permite sin quitarle sus derechos de DDL. [Privilegios del propietario en PostgreSQL](https://www.postgresql.org/docs/17/ddl-priv.html).

**Cierre, en una transacción breve:**

```sql
BEGIN;
SET LOCAL ROLE pos_owner;
-- Lista completa de tablas pos originales, obtenida y validada desde catálogos.
LOCK TABLE <tablas_pos_originales> IN ACCESS EXCLUSIVE MODE NOWAIT;
REVOKE INSERT, UPDATE, DELETE, TRUNCATE
  ON <tablas_pos_originales> FROM pos_owner;
REVOKE SELECT ON pos.idempotency_requests FROM pos_owner;
COMMIT;
```

Los LOCK solo sirven para drenar transacciones anteriores y hacer el corte de permisos sin una carrera; se liberan en ese COMMIT, **antes del primer DDL**. Si hay una transacción o lector incompatible, NOWAIT rechaza el cierre y todo se revierte. No se cancela ni termina una sesión ajena para continuar.

La exclusión durante los tres archivos procede de las ACL ya confirmadas, no de un bloqueo de lectura persistente ni de un advisory lock:

- `pos_owner` no puede escribir en las tablas originales, incluso si un escritor ignora cualquier señal de mantenimiento.
- El acceso inicial de los comandos a idempotencia queda denegado. Además, `require_staff` usa FOR SHARE sobre perfiles, que requiere UPDATE: la retirada de UPDATE impide que las RPC normales avancen. Esto también protege las nuevas tablas de 006/007: sus RPC pasan por el control de personal/idempotencia antes de mutar datos.
- Los contactos y recordatorios no dependen todos de idempotencia. Sus funciones también ejecutan con `pos_owner`, y la retirada de DML sobre sus tablas bloquea esos caminos. La prueba incluye el scheduler, no solo ventas.
- Las nuevas concesiones EXECUTE a `authenticated` dentro de 006/007 no restauran los permisos de tabla del propietario, por lo que no abren una carrera entre COMMIT y la validación.
- Se conservan SELECT en las demás tablas, REFERENCES, TRIGGER y los derechos inherentes de propietario necesarios para el DDL. No se cambia ningún propietario, RLS, función, política o rol. No se conceden privilegios a PUBLIC, anon o authenticated para establecer la barrera.

**Límite obligatorio:** esto contiene los escritores de aplicación inventariados, no un superusuario o administrador capaz de volver a concederse permisos. Producción requiere un único operador administrativo, sin SQL Editor, otros migradores o integraciones administrativas concurrentes. La actividad inesperada causa parada. Una definición, rol o concesión fuera del inventario exige revisión antes de cortar permisos; no se asume cobertura universal por el nombre de un rol.

Inventariar todos los escritores/roles/funciones y accesos administrativos; guardar las ACL y su matriz efectiva fuera de Git. Cualquier diferencia no revisada detiene el procedimiento.
2. Con un solo operador, efectuar el corte breve NOWAIT y las revocaciones descritas. Confirmar COMMIT, matriz de permisos cerrada y ausencia de transacciones/bloqueos restantes. Si falla antes del COMMIT, revertir y detenerse.
3. Ejecutar auditorías READ ONLY y terminarlas con COMMIT. Inspeccionar actividad/bloqueos antes de cada DDL. Mantener `lock_timeout=5s`, `statement_timeout=120s` y ON_ERROR_STOP; NOWAIT para el drenaje. No ampliar tiempos automáticamente ni cancelar sesiones ajenas para pasar.
4. Aplicar 006 → validar → registrar; repetir 007 y 008. La barrera permanece confirmada entre todos los COMMIT. Comparar registros, saldos, secuencias y el cálculo de la vista antes de avanzar; distinguir las ACL temporalmente cerradas de las ACL finales.
5. Ejecutar la auditoría final. Solo si el estado y los COMMIT son conocidos, restaurar las concesiones exactas capturadas: para este estado, INSERT/UPDATE/DELETE/TRUNCATE al propietario en las tablas originales y SELECT en idempotencia. No utilizar GRANT ALL ni conceder a otros roles. Confirmar COMMIT y comparar la matriz final, RLS, propietarios, historial y datos. Las tablas nuevas mantienen las ACL especificadas por las migraciones.
6. Finalizar la ventana solo tras esa comprobación. Los scripts de cierre/restauración y su captura deben estar disponibles para un segundo proceso controlado de recuperación antes de iniciar.

**Errores y desconexiones:** antes de ejecutar DDL o con rollback inequívoco y esquema verificado, se puede restaurar de forma controlada la ACL original. Si hay un COMMIT ambiguo, una versión parcial o se pierde el controlador, no se reabre automáticamente la escritura: la barrera queda cerrada, sin bloqueos de lectura persistentes. Se reconcilian objetos/historial y se libera con la captura revisada. Se probó esa liberación controlada; un watchdog que concediera permisos a ciegas sería inseguro. No se restaura ni elimina información comercial para liberar la ventana.
